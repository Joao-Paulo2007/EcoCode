# ADR-041: Fazer o front-end em HTML, CSS e JavaScript puros dentro de resources

- **Status:** Aceita
- **Data:** 2026-10-27
- **Autores:** Grupo do projeto

## Contexto

A interface do EcoCode era só o menu do terminal. Um membro do grupo criou as telas para o
navegador. Era preciso decidir com que tecnologia essas telas seriam feitas e onde elas
ficariam no projeto.

## Decisão

> Vamos fazer o front-end com HTML, CSS e JavaScript puros, sem framework, guardado em
> `src/main/resources/frontend_ecocode`, para ser servido pelo próprio Spring Boot.

```text
src/main/resources/frontend_ecocode/
├── html/   index.html, login.html, cadastro.html, Tela.html
├── css/    base.css, Index.css, login.css, cadastro.css, telaPrincipal.css, modal.css
└── js/     tela.js
```

**Telas**

| Página | O que tem hoje |
| --- | --- |
| `index.html` | Página inicial, com botão que leva ao `login.html` |
| `login.html` | Formulário de e-mail e senha |
| `cadastro.html` | Formulário de e-mail, data de nascimento, senha e confirmação |
| `Tela.html` | Tela principal: filtro por categoria e duas janelas (modais), uma para cadastrar resíduo e outra para cadastrar pessoa |

**O que o `tela.js` faz**

- Abre e fecha os modais (botão, X, clique no fundo e tecla Esc) e limpa o formulário ao
  fechar.
- Coloca a máscara `000.000.000-00` no CPF enquanto se digita.
- Avisa quando a senha e a confirmação são diferentes.
- Ao enviar um formulário, monta um objeto com os dados e só mostra no console
  (`console.log`). Ainda não envia nada para o back-end (há um `TODO` no código).

- O CSS foi dividido em um arquivo base (`base.css`), comum a todas as páginas, e um arquivo
  por tela.
- As páginas apontam umas para as outras com caminhos relativos (`../css/base.css`,
  `../js/tela.js`).

## Alternativas consideradas

### Alternativa 1: React, Angular ou Vue

- **Prós:** componentes reaproveitáveis e muito usados no mercado.
- **Contras:** exigem Node, build próprio e outra curva de aprendizado ao mesmo tempo que o
  Spring.
- **Por que não foi escolhida:** HTML, CSS e JS puros bastam para o tamanho das telas e não
  precisam de ferramenta extra.

### Alternativa 2: Templates gerados no servidor (Thymeleaf)

- **Prós:** o Spring monta a página já com os dados.
- **Contras:** mistura a tela com o back-end e prende o front ao Java.
- **Por que não foi escolhida:** o grupo quis front e back separados, conversando por HTTP.

### Alternativa 3: Front-end num projeto separado

- **Prós:** separação total; cada parte com seu repositório.
- **Contras:** dois projetos para rodar e problemas de CORS (o navegador bloqueia chamadas
  entre endereços diferentes, a menos que o servidor libere).
- **Por que não foi escolhida:** servido pelo Spring, front e back ficam no mesmo endereço e
  sobem juntos.

## Consequências

### Positivas

- O front pode ser aberto direto no navegador, mesmo sem o servidor, para testar o visual.
- Nenhuma ferramenta nova além do navegador.
- Quem mexe no front não precisa entender Java.

### Negativas

- **O Spring não serve essa pasta do jeito que está.** Por padrão, o Spring Boot só entrega
  arquivos de `src/main/resources/static/` (ou `public/`). Com o servidor rodando,
  `http://localhost:8080/html/index.html` não vai abrir a página.
- Os formulários ainda não conversam com o back-end.

### Neutras

- O que o front envia e o que o back espera precisam combinar. Hoje não combinam:

| Campo | Front envia | Back espera |
| --- | --- | --- |
| Tipo do resíduo | `"PCs e Notebooks"`, `"Celular tablet"`... | `TipoResiduo.COMPUTADORES`, `CELULARES`... |
| Quantidade | `quantidade` (texto do formulário) | `int` |
| Cargo | `"gerente"`, `"funcionario"` | `CargoUsuario.GERENTE`, `FUNCIONARIO` |
| CPF | com máscara `000.000.000-00` | qualquer formato; o back limpa (ADR-027) |
| Nascimento | `AAAA-MM-DD` (campo `date`) | `DD/MM/AAAA` na tela do terminal (ADR-029) |

## Riscos e pendências

- [ ] Mover a pasta para `src/main/resources/static/` (ou configurar
  `spring.web.resources.static-locations=classpath:/frontend_ecocode/` no
  `application.properties`).
- [ ] Trocar os `console.log` dos formulários por `fetch(...)` para os controllers (ADR-038).
- [ ] Combinar os valores dos `<option>` com os nomes dos enums (`COMPUTADORES`, `GERENTE`...)
  ou converter no controller.
- [ ] Ligar o login (`login.html`) ao back-end; o login de usuário ainda não existe.
- [x] O `login.html` e o `cadastro.html` pedem e-mail, mas o usuário é identificado pelo CPF
  (ADR-022). Decidir qual dos dois será usado para entrar (decidido no ADR-043: e-mail).
- [ ] Criar no front as telas que faltam: listagem, busca, edição e exclusão de resíduos, e as
  cifras.
- [ ] O `Tela.html` tem `T` maiúsculo e o `Index.css` tem `I` maiúsculo. No Windows funciona,
  mas em servidor Linux maiúscula e minúscula fazem diferença.

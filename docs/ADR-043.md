# ADR-043: Fazer o login por e-mail e senha, devolvendo o usuário que entrou

- **Status:** Aceita
- **Data:** 2026-10-28
- **Autores:** Grupo do projeto

## Contexto

O módulo de usuários já existia (ADR-022), com a senha guardada cifrada pela César (ADR-023),
mas o programa abria direto no menu de resíduos: qualquer pessoa usava tudo, e não havia como
saber quem estava usando. O front-end (ADR-041) também tem uma tela de login que pede e-mail
e senha.

A primeira versão do login tinha três erros que impediam a entrada:

- comparava as senhas com `==`, que em `String` compara se são o mesmo objeto, e não o texto;
- guardava o resultado numa variável nova dentro do `while`, e o loop nunca terminava;
- não tratava a exceção de e-mail inexistente, que derrubava o programa.

## Decisão

> Vamos identificar a pessoa pelo e-mail e pela senha, e fazer o login devolver o `Usuario`
> que entrou, para as telas seguintes saberem quem está usando o sistema.

| Classe | O que faz |
| --- | --- |
| `GerenciarUsuariosRepository.buscarEmail` | Procura o usuário pelo e-mail, sem diferenciar maiúsculas; devolve `null` se não achar |
| `GerenciarUsuariosService.buscarEmail` | Valida o formato e lança exceção se o usuário não existir |
| `Util/LogarUsuario.logarUsuario(email, senha)` | Valida os dados, busca pelo e-mail e compara a senha; devolve o `Usuario` ou lança exceção |
| `TelaTerminal/TelaUsuarioTerminal` | Pede e-mail e senha até o login dar certo e entrega o usuário para a tela de resíduos |

- **Comparação da senha:** a senha digitada é cifrada e comparada com a guardada usando
  `equals`. A senha guardada nunca é decifrada.
- **Mensagem de falha:** é a mesma para e-mail inexistente e para senha errada ("Falha no
  Login, verifique o email e senha digitados"), para não revelar quais e-mails estão
  cadastrados.
- **Usuário logado:** a tela de resíduos recebe o `Usuario` no construtor e o guarda como
  `usuarioLogado`. É o que permite mostrar o nome no menu e liberar opções pelo cargo
  (ADR-045).
- O `Main` cadastra três usuários de teste (dois gerentes e uma funcionária) só se eles ainda
  não existirem, e então abre a tela de login.

## Alternativas consideradas

### Alternativa 1: Login pelo CPF

- **Prós:** o CPF já é a chave do usuário (ADR-022, ADR-027), e a busca é direta no `Map`.
- **Contras:** CPF é um dado sensível para digitar toda hora; o front já pede e-mail.
- **Por que não foi escolhida:** e-mail é o padrão de login e combina com a tela do front.

### Alternativa 2: Login devolvendo só `true` ou `false`

- **Prós:** foi a primeira versão; simples.
- **Contras:** a tela sabe que alguém entrou, mas não quem; seria preciso buscar o usuário de
  novo.
- **Por que não foi escolhida:** devolver o usuário resolve as duas coisas de uma vez.

### Alternativa 3: Decifrar a senha guardada e comparar com a digitada

- **Prós:** também funciona com a César.
- **Contras:** não funcionaria com um hash de verdade, que não pode ser desfeito.
- **Por que não foi escolhida:** cifrar a digitada e comparar é o mesmo caminho que um hash
  vai exigir quando a César for trocada.

## Consequências

### Positivas

- Só entra quem tem cadastro, e o sistema sabe quem está usando.
- E-mail errado ou inexistente não derruba mais o programa.

### Negativas

- A busca por e-mail percorre todos os usuários, porque o `Map` é organizado por CPF. Com
  poucos usuários isso não se nota.
- A senha continua protegida só pela César (ADR-023), que é fácil de quebrar.
- Não existe "sair e entrar com outro usuário": para trocar, é preciso fechar o programa.

### Neutras

- O pacote das telas passou de `Tela` para `TelaTerminal`.

## Riscos e pendências

- [ ] Trocar a César por um hash de senha (BCrypt, por exemplo) antes de qualquer uso real.
- [ ] Limitar tentativas de login seguidas.
- [ ] Criar o endpoint de login no Spring e ligar o `login.html` (ADR-041).

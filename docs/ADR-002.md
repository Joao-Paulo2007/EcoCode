# ADR-002: Concentrar tela, dados e geração de código na classe Cadastro

- **Status:** Substituída por ADR-010
- **Data:** 2026-10-06
- **Autores:** Grupo do projeto (versão 1.0 publicada por João Paulo)

## Contexto

O módulo tem poucas funcionalidades: cadastrar, listar, contar e classificar. Para a
primeira versão, o grupo precisava de algo funcionando rápido, com o menor número de
classes possível.

## Decisão

> Vamos colocar numa única classe, `Cadastro`, a leitura do teclado, a lista de resíduos,
> a geração de códigos e os registros iniciais.

A divisão da versão 1.0 fica assim:

| Classe | Responsabilidades |
| --- | --- |
| `Main` | Menu e despacho das opções |
| `Cadastro` | Telas (`Scanner` e `println`), `ArrayList` de resíduos, `gerarCodigo`, contagens, seed |
| `Classificador` | Tipo para resto e código para categoria (ADR-007) |
| `Residuos` | Dados de um resíduo |

## Alternativas consideradas

### Alternativa 1: Arquitetura em camadas (tela, serviço, repositório)

- **Prós:** cada classe com um motivo só para mudar; trocar o armazenamento ou a tela sem
  mexer nas regras.
- **Contras:** mais arquivos e interfaces para um programa pequeno.
- **Por que não foi escolhida:** parecia cerimônia demais para a primeira entrega.

## Consequências

### Positivas

- Fácil de ler de cima a baixo: tudo sobre resíduos está num arquivo.
- Primeira versão entregue rápido.

### Negativas

- `Cadastro` tem quatro motivos diferentes para mudar (tela, armazenamento, regra de
  código, dados de teste). Qualquer alteração mexe nela.
- Não dá para testar a geração de código ou o cadastro sem passar pelo `Scanner`.
- Não há validação de dados: quantidade 0 ou negativa é aceita e entra na lista.
- Para incorporar o módulo ao app do grupo, como o enunciado pede, seria preciso separar
  a lógica da tela de terminal.

## Riscos e pendências

- [ ] Esta é a decisão que mais pesa a favor de uma refatoração em camadas quando entrarem
  edição, exclusão e as cifras da Missão 03.

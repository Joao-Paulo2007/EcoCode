# ADR-038: Usar Spring Boot como servidor do back-end

- **Status:** Aceita
- **Data:** 2026-10-27
- **Autores:** Grupo do projeto

## Contexto

Até aqui o EcoCode era um programa de terminal (ADR-001): o `Main` mostrava um menu, a tela
lia o teclado e chamava os services. Um membro do grupo fez um front-end em HTML, CSS e
JavaScript (ADR-041), e um navegador não consegue chamar classes Java diretamente. Ele só
conversa com um servidor, por requisições HTTP.

O back-end precisa então ficar "ouvindo" numa porta e responder às requisições do front. O
grupo ainda está estudando o framework, então a decisão desta etapa é preparar a base e
confirmar que o servidor sobe; os endpoints de verdade vêm depois.

## Decisão

> Vamos transformar o projeto num projeto Spring Boot, que sobe um servidor web embutido
> (Tomcat) e expõe os services do EcoCode por meio de controllers REST.

**Mudanças no `pom.xml`**

| Item | Antes | Agora |
| --- | --- | --- |
| Projeto pai (`<parent>`) | nenhum | `spring-boot-starter-parent` 4.0.6 |
| Versão do Java | 25 | 25 (agora em `<java.version>`) |
| Servidor web | nenhum | `spring-boot-starter-web` (Spring MVC + Tomcat + Jackson) |
| Plugin de build | nenhum | `spring-boot-maven-plugin` |
| `dotenv-java` e `gson` | mantidos | mantidos |

**Classes novas**

| Classe | Papel |
| --- | --- |
| `ServidorApplication` | Ponto de entrada do servidor. Tem `@SpringBootApplication` e chama `SpringApplication.run(...)` |
| `Controller/TesteController` | Controller de teste: `GET /oi` devolve "O back tá vivo!" |

- O `@SpringBootApplication` faz o Spring procurar componentes a partir do pacote da classe,
  `backend_ecocode` (ADR-039), e por isso a classe fica na raiz desse pacote.
- O servidor sobe na porta padrão, 8080. Com ele rodando, abrir `http://localhost:8080/oi` no
  navegador deve mostrar a frase de teste.
- O `Main` do terminal continua existindo e funcionando. São dois pontos de entrada no mesmo
  projeto: `Main` para o menu, `ServidorApplication` para o servidor.

**Como a camada nova se encaixa nas antigas (ADR-010)**

```text
Navegador (HTML/JS)  --HTTP-->  Controller  -->  Service  -->  Repository  -->  arquivos JSON
Terminal             --------->  Tela        -->  Service  -->  Repository  -->  arquivos JSON
```

O controller ocupa, para o navegador, o lugar que a tela ocupa para o terminal: recebe o
pedido, chama o service e devolve a resposta. A regra de negócio continua no service.

## Alternativas consideradas

### Alternativa 1: Servidor HTTP do próprio Java (`com.sun.net.httpserver`)

- **Prós:** nenhuma dependência nova; dá para entender cada linha.
- **Contras:** converter JSON, tratar rotas, erros e arquivos estáticos ficaria todo à mão.
- **Por que não foi escolhida:** o grupo quer aprender um framework usado no mercado, e o
  Spring resolve essas partes prontas.

### Alternativa 2: Javalin ou Spark Java

- **Prós:** mais leves e com menos "mágica" que o Spring.
- **Contras:** menos material de estudo em português e menos usados em vagas.
- **Por que não foi escolhida:** o Spring Boot é o padrão de back-end em Java.

### Alternativa 3: Continuar só no terminal

- **Prós:** nenhuma mudança.
- **Contras:** o front-end feito pelo grupo não teria com quem conversar.
- **Por que não foi escolhida:** a interface no navegador passou a fazer parte do projeto.

## Consequências

### Positivas

- O projeto passa a ter um servidor que o front-end pode chamar.
- As camadas que já existiam (service, repository, persistência) são reaproveitadas sem
  mudar a regra de negócio.
- O `spring-boot-maven-plugin` permite gerar um `.jar` executável com tudo dentro.

### Negativas

- O projeto deixa de ser "sem dependências" (ADR-001): o Spring traz muitas bibliotecas e
  deixa o build e a primeira execução mais lentos.
- O grupo precisa aprender conceitos novos: beans, injeção de dependência, anotações,
  controllers.
- O `spring-boot-starter-web` já traz o Jackson para converter JSON, e o projeto continua com
  o Gson para os arquivos. São duas bibliotecas de JSON no mesmo projeto.

### Neutras

- Para rodar o servidor: `mvn spring-boot:run`, ou executar `ServidorApplication` pela IDE.
- O nome do projeto no `pom.xml` (`org.example:Projeto_APP_ReciclagemDeLixoEletronico`)
  continua o mesmo.

## Riscos e pendências

- [ ] Criar os controllers de verdade: resíduos (cadastrar, listar, buscar, editar, excluir,
  filtrar por categoria, quantidades), usuários (cadastrar, login) e cifras.
- [ ] Apagar o `TesteController` quando o primeiro controller real funcionar.
- [ ] Decidir se o `Main` do terminal continua no projeto final ou sai quando o front estiver
  completo. Enquanto os dois existirem, não rodar os dois ao mesmo tempo: cada um carrega os
  arquivos JSON na memória e um pode sobrescrever o que o outro gravou.
- [ ] Conferir se o Spring Boot 4.0.6 compila com o Java 25 instalado nas máquinas do grupo.
- [ ] Criar `src/main/resources/application.properties` quando for preciso mudar porta,
  caminho dos arquivos estáticos ou outras configurações.

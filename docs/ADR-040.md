# ADR-040: Marcar services e repositórios como componentes do Spring e sincronizar os repositórios

- **Status:** Aceita
- **Data:** 2026-10-27
- **Autores:** Grupo do projeto

## Contexto

No terminal, só existe uma pessoa usando o programa, e cada ação acontece uma depois da
outra. Num servidor, o Spring atende cada requisição HTTP numa thread própria, então dois
usuários podem cadastrar um resíduo no mesmo instante.

Os repositórios guardam os dados num `Map` em memória (ADR-011, ADR-036) e regravam o arquivo
JSON a cada mudança (ADR-024, ADR-026). `LinkedHashMap` e `TreeMap` não são seguros para uso
por várias threads ao mesmo tempo: duas gravações simultâneas podem corromper o mapa ou deixar
o arquivo com só uma das mudanças.

## Decisão

> Vamos anotar os services com `@Service` e os repositórios com `@Repository`, para que o
> Spring os reconheça, e marcar como `synchronized` os métodos dos repositórios que leem ou
> alteram o `Map`.

| Classe | Anotação | Métodos `synchronized` |
| --- | --- | --- |
| `GerenciarResiduosService` | `@Service` | nenhum |
| `GerenciarUsuariosService` | `@Service` | nenhum |
| `GerenciarResiduosRepository` | `@Repository` | `salvar`, `editar`, `excluir`, `listar` |
| `GerenciarUsuariosRepository` | `@Repository` | `cadastrar`, `editar`, `listar`, `remover` |

- Com `synchronized`, só uma thread por vez entra num desses métodos do mesmo repositório. As
  outras esperam a vez, como uma fila no caixa.
- Por enquanto, os services ainda criam os repositórios com `new` e a tela ainda cria o seu
  service, como antes (decisão do grupo de não usar construtores com parâmetros nesta etapa).
  As anotações deixam o projeto pronto para trocar o `new` pela injeção do Spring.

## Alternativas consideradas

### Alternativa 1: Trocar o `Map` por `ConcurrentHashMap`

- **Prós:** o próprio mapa fica seguro para várias threads, sem `synchronized`.
- **Contras:** não mantém a ordem de cadastro (ADR-036) e não protege a gravação do arquivo,
  que acontece logo depois de mexer no mapa.
- **Por que não foi escolhida:** o `synchronized` protege o mapa e o arquivo juntos.

### Alternativa 2: Não sincronizar

- **Prós:** nenhuma mudança.
- **Contras:** funciona nos testes com uma pessoa, mas pode falhar quando houver requisições
  simultâneas, de um jeito difícil de reproduzir.
- **Por que não foi escolhida:** o servidor atende várias requisições ao mesmo tempo.

### Alternativa 3: Injetar os repositórios já nesta etapa

- **Prós:** um único repositório por tipo de dado no servidor inteiro.
- **Contras:** exige construtores com parâmetro ou `@Autowired`, assunto que o grupo ainda vai
  estudar.
- **Por que não foi escolhida:** fica para quando os controllers forem criados (ver
  pendências).

## Consequências

### Positivas

- O Spring encontra e gerencia os services e repositórios.
- Duas requisições ao mesmo repositório não se atropelam no `Map` nem no arquivo.

### Negativas

- **Ainda existem instâncias duplicadas.** O Spring cria um `GerenciarResiduosRepository`
  próprio (por causa do `@Repository`), e cada `GerenciarResiduosService` criado com `new`
  cria outro. O `Main` também cria o seu service e a tela cria mais um. Cada cópia carrega o
  arquivo na memória e grava por cima das outras, e o `synchronized` não ajuda, porque ele só
  vale dentro do mesmo objeto. Com os resíduos, também existem dois `GerarCodigoResiduo`, que
  podem gerar o mesmo código.
- Enquanto uma thread grava, as outras esperam. Com poucos usuários isso não se nota.

### Neutras

- Os services não precisaram de `synchronized`: eles não guardam dados próprios, só chamam o
  repositório.

## Riscos e pendências

- [ ] Trocar o `new` dos repositórios nos services pela injeção do Spring (construtor recebendo
  o repositório), para existir uma instância só de cada um no servidor.
- [ ] Fazer o mesmo com o `GerarCodigoResiduo`, ou sincronizar o `gerarCodigo`, para que duas
  requisições não recebam o mesmo código.
- [ ] Fazer o `Main` reaproveitar o service da tela, em vez de criar outro (dois services =
  dois repositórios no terminal também).
- [ ] Remover o campo `private Constantes constante = new Constantes();` dos dois
  repositórios: as constantes são estáticas e o campo não é usado.

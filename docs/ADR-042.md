# ADR-042: Manter a persistência em arquivos JSON e adiar o banco de dados

- **Status:** Aceita
- **Data:** 2026-10-28
- **Autores:** Grupo do projeto

## Contexto

Com o Spring Boot (ADR-038), o grupo começou a trocar os arquivos JSON (ADR-024, ADR-026) por
um banco PostgreSQL. Chegaram a ser escritas classes de persistência com JDBC
(`PersistenciaBancoResiduos`, `PersistenciaBancoUsuarios`), um `id` gerado pelo banco no
`Residuo` e no `Usuario`, a leitura de um `DATABASE_URL` na `Configuracao` e o driver do
PostgreSQL no `pom.xml`.

Ao mesmo tempo, o front-end (ADR-041) ainda não conversa com o back-end, e o grupo está
começando a estudar Spring. Mexer no banco, no Spring e no front de uma vez multiplicaria os
lugares onde algo pode dar errado.

## Decisão

> Vamos continuar salvando em arquivos JSON por enquanto e deixar o banco de dados para
> depois que o front-end estiver ligado ao back-end.

O que foi desfeito:

| Item | Situação |
| --- | --- |
| `PersistenciaBancoResiduos`, `PersistenciaBancoUsuarios`, `PersistenciaBancoDeDadosInterface` | Removidas do projeto |
| Campo `id` no `Residuo` e no `Usuario` | Removido |
| Repositórios com `Map` + `PersistenciaArquivo` (ADR-024, ADR-026, ADR-040) | Mantidos como estavam |
| Dependência `org.postgresql` no `pom.xml` | Remover |
| `DadosBanco` e `getDadosBanco()` na `Configuracao` | Remover |

O que já se sabe para quando o banco voltar:

- As tabelas `residuo` e `usuario` teriam um `id` gerado pelo banco
  (`GENERATED ALWAYS AS IDENTITY`) como chave primária, com o código do resíduo e o CPF como
  colunas `UNIQUE`. O id serve para ligar tabelas; o usuário continua buscando pelo código e
  pelo CPF.
- Os repositórios podem passar a só repassar as chamadas para o banco, sem `Map`, o que
  também resolve as instâncias duplicadas do ADR-040.
- O `ORDER BY id` mantém a listagem na ordem de cadastro (ADR-036).

## Alternativas consideradas

### Alternativa 1: Terminar o banco agora

- **Prós:** os dados ficam num lugar só, seguro para vários acessos ao mesmo tempo.
- **Contras:** exige um servidor PostgreSQL rodando para cada membro do grupo testar, e o
  front ainda nem chama o back.
- **Por que não foi escolhida:** o próximo passo do projeto é o front, e o JSON já atende.

### Alternativa 2: Usar os dois ao mesmo tempo, com uma opção para escolher

- **Prós:** dá para testar o banco sem perder o arquivo.
- **Contras:** duas persistências para manter e testar.
- **Por que não foi escolhida:** complexidade sem necessidade nesta etapa.

## Consequências

### Positivas

- O projeto continua rodando em qualquer máquina, sem instalar banco.
- O grupo aprende uma coisa por vez: primeiro Spring e front, depois banco.

### Negativas

- Continuam valendo os riscos dos arquivos: instâncias duplicadas do repositório podem gravar
  uma por cima da outra (ADR-040).

### Neutras

- O código do banco pode ser guardado numa branch (por exemplo, `banco-de-dados`) para ser
  retomado depois.

## Riscos e pendências

- [ ] Remover o driver `org.postgresql` do `pom.xml` e o `getDadosBanco()` da `Configuracao`.
- [ ] Remover as pastas antigas que apareceram soltas em `src/main/java` (`Cadastro`,
  `Domain`, `Util`, ...), fora do `backend_ecocode`.
- [ ] Reavaliar o banco quando o front estiver chamando os controllers.

## Referências

- ADR-024 e ADR-026 (arquivos JSON), ADR-036 (ordem de cadastro), ADR-038 (Spring Boot),
  ADR-040 (instâncias duplicadas), ADR-041 (front-end).

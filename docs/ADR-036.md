# ADR-036: Listar os resíduos por ordem de cadastro ou por ordem de código

- **Status:** Aceita
- **Data:** 2026-10-26
- **Autores:** Grupo do projeto

## Contexto

O repositório guardava os resíduos num `TreeMap` (ADR-011), que mantém as chaves ordenadas.
Por isso a listagem sempre saía em ordem de código, e não havia como ver os resíduos na ordem
em que foram cadastrados. O grupo quis oferecer as duas ordens.

## Decisão

> Vamos guardar os resíduos num `LinkedHashMap`, que mantém a ordem de cadastro, e ordenar por
> código no service apenas quando essa ordem for pedida.

| Camada | O que faz |
| --- | --- |
| `GerenciarResiduosRepository` | Usa `LinkedHashMap` no lugar do `TreeMap`; `listar()` devolve na ordem de cadastro |
| `GerenciarResiduosService.listar()` | Repassa a lista na ordem de cadastro |
| `GerenciarResiduosService.listarPorCodigo()` | Ordena a cópia da lista pelo valor numérico do código (`Integer.parseInt`) |
| `TelaCadastroResiduoTerminal.listar_residuos()` | Pergunta a ordem (1 = cadastro, 2 = código); qualquer outra resposta lista por cadastro |

- A ordem de cadastro sobrevive ao fechamento do programa: o arquivo é gravado na ordem do
  `Map` e, ao abrir, os resíduos são inseridos na mesma ordem.
- Editar um resíduo com `put` numa chave existente não muda a posição dele.
- A ordenação por código trabalha numa cópia (`listar()` do repositório devolve
  `new ArrayList<>(...)`), então não altera os dados guardados.

## Alternativas consideradas

### Alternativa 1: Manter o `TreeMap` e ordenar por cadastro no service

- **Prós:** nenhuma mudança no repositório.
- **Contras:** o resíduo não guarda nenhuma informação de quando foi cadastrado; não haveria
  como reconstruir a ordem.
- **Por que não foi escolhida:** a ordem precisa ser guardada em algum lugar.

### Alternativa 2: Campo com data e hora de cadastro no `Residuo`

- **Prós:** a ordem fica registrada no próprio dado e pode ser exibida na tela.
- **Contras:** exige um adaptador de `LocalDateTime` no Gson, e os resíduos já salvos ficariam
  sem data.
- **Por que não foi escolhida:** a ordem do `LinkedHashMap` resolve com uma linha; a data pode
  vir depois, se for preciso exibi-la.

### Alternativa 3: Duas opções separadas no menu principal

- **Prós:** nenhuma pergunta extra na tela.
- **Contras:** o menu principal ficaria maior.
- **Por que não foi escolhida:** a escolha da ordem pertence à listagem.

## Consequências

### Positivas

- O usuário escolhe a ordem da listagem.
- A busca por código continua direta, como no `TreeMap`.

### Negativas

- Com o gerador atual (ADR-032), cada código novo é maior que o anterior, então as duas ordens
  coincidem. Elas só diferem para resíduos criados por geradores anteriores ou com códigos fora
  de sequência.
- Os resíduos gravados enquanto o repositório usava `TreeMap` continuam no arquivo em ordem de
  código.

### Neutras

- A opção 2 da tela converte cada código para número a cada listagem.

## Riscos e pendências

- [ ] Confirmar que o repositório usa `LinkedHashMap`: mover um resíduo no `rediduos.json` e
  verificar se a ordem de cadastro muda e a de código não.

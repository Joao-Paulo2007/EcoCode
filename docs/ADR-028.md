# ADR-028: Reunir as validações do usuário na classe ValidacoesUsuario

- **Status:** Aceita
- **Data:** 2026-10-24
- **Autores:** Grupo do projeto

## Contexto

As validações do `Usuario` estavam escritas uma a uma dentro do construtor, e o CPF era
validado duas vezes seguidas (ADR-022). O formato do e-mail não era conferido: qualquer texto
não vazio era aceito.

## Decisão

> Vamos reunir as validações do usuário na classe `ValidacoesUsuario`, chamada pelo construtor
> do `Usuario`, e passar a validar o formato do e-mail.

| Método | Valida |
| --- | --- |
| `validarUsuario(...)` | Chama as validações abaixo, nessa ordem |
| `validarEmailUsuario` | E-mail obrigatório e com formato válido (`ValidarEmail.ehValido`) |
| `validarCpfUsuario` | CPF válido pelos dígitos verificadores (`ValidadorCpf.ehValido`), uma vez só |
| `validarNomeUsuario` | Nome completo obrigatório |
| `validarCargoUsuario` | Cargo obrigatório |

- Todas as falhas lançam `IllegalArgumentException`, a mesma exceção usada nos resíduos
  (ADR-014), para que a tela trate todas com um único `catch`.
- O `Usuario` guarda uma instância estática de `ValidacoesUsuario`.
- A data de nascimento continua sendo validada no próprio construtor, ao ser convertida para
  `LocalDate`.

## Alternativas consideradas

### Alternativa 1: Manter as validações no construtor do `Usuario`

- **Prós:** tudo num lugar só.
- **Contras:** o construtor cresce a cada regra nova.
- **Por que não foi escolhida:** separar deixa o construtor curto e as regras nomeadas.

### Alternativa 2: Lançar erros diferentes por tipo de falha

- **Prós:** a tela poderia reagir de forma diferente a cada erro.
- **Contras:** mais tipos de exceção para tratar. Uma primeira versão usava
  `IllegalAccessError` para o e-mail, que é um erro grave do Java, não é pego pelo `catch` da
  tela e derrubaria o programa.
- **Por que não foi escolhida:** uma única exceção com mensagem clara basta.

## Consequências

### Positivas

- O construtor do `Usuario` ficou curto.
- E-mails sem formato válido são recusados.
- Cada regra tem um método com nome próprio.

### Negativas

- As validações só rodam no construtor: os setters do `editar` continuam aceitando nome e
  e-mail vazios ou inválidos.
- Os usuários lidos do arquivo não passam pelas validações, porque o Gson não chama o
  construtor (ADR-026).

### Neutras

- `ValidacoesUsuario` não guarda estado; seus métodos poderiam ser `static`.

## Riscos e pendências

- [ ] Chamar as validações também no `editar`, antes de usar os setters.
- [ ] Impedir data de nascimento futura e exigir senha no cadastro.

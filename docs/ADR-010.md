# ADR-010: Separar o módulo em camadas (tela, service, repository e domínio)

- **Status:** Aceita
- **Data:** 2026-10-22
- **Autores:** Grupo do projeto

## Contexto

Na versão 1.0, a classe `Cadastro` concentrava a tela, a lista de resíduos, a geração de
código e os registros iniciais (ADR-002). Com a entrada de busca, edição, exclusão e da
cifra da Missão 03, essa classe passaria a ter ainda mais motivos para mudar. O enunciado
também pede que o módulo possa ser incorporado depois ao aplicativo do grupo, o que exige
separar a lógica da tela de terminal.

## Decisão

> Vamos organizar o código em camadas, em que cada camada só conversa com a de baixo:
> tela, service, repository e domínio.

| Pacote | Conteúdo | Responsabilidade |
| --- | --- | --- |
| `Tela` | `TelaCadastroResiduoTerminal` | Ler o teclado, mostrar resultados, tratar exceções para o usuário |
| `Service` | `GerenciarResiduosService` | Regras que dependem de outros dados (código livre, existência do resíduo) |
| `Repository` | `GerenciarResiduosRepository` | Guardar, buscar, listar e remover, sem regra nenhuma |
| `Domain` | `Residuo`, `TipoResiduo`, `ServiceResiduosInterface`, `RepositoryResiduosInterface` | O que as coisas são e os contratos entre as camadas |
| `Util` | `GerarCodigoResiduo`, `CifraCesar`, `Configuracao` | Apoio usado pelas camadas acima |

O fluxo é sempre tela, service, repository. A tela nunca acessa o repositório direto,
mesmo quando o service só repassa o resultado (como no `listar`).

## Alternativas consideradas

### Alternativa 1: Manter a classe única da versão 1.0

- **Prós:** nenhum trabalho de refatoração.
- **Contras:** cada funcionalidade nova aumentaria a classe `Cadastro`; impossível trocar o
  armazenamento ou a tela sem mexer nas regras.
- **Por que não foi escolhida:** o projeto vai crescer com usuários, persistência e cifras.

### Alternativa 2: Arquitetura hexagonal (portas e adaptadores)

- **Prós:** isola ainda mais o domínio do mundo externo.
- **Contras:** mais interfaces e cerimônia; o único "mundo externo" hoje é o terminal.
- **Por que não foi escolhida:** complexidade maior que a necessidade atual.

## Consequências

### Positivas

- Cada classe tem um motivo só para mudar.
- O armazenamento pode trocar (memória, JSON, banco) criando outra implementação do
  repositório.
- As regras ficam testáveis sem passar pelo `Scanner`.

### Negativas

- Mais arquivos para um programa pequeno.
- O service cria o repositório com `new GerenciarResiduosRepository()` e a tela cria o
  service com `new`. Na prática, as camadas ainda dependem das classes concretas, e trocar o
  repositório exige editar o service.

### Neutras

- As interfaces ficam no pacote `Domain`, e as implementações nos pacotes `Service` e
  `Repository`.

## Riscos e pendências

- [ ] Fazer o service receber o repositório pela interface, no construtor, antes da
  persistência em JSON.

## Referências

- Substitui o ADR-002 (classe `Cadastro` centralizada).
- ADR-011 (repositório com `Map`).

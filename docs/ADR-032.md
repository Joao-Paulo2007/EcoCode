# ADR-032: Calcular o próximo código a partir do último gerado, de qualquer tipo

- **Status:** Aceita
- **Data:** 2026-10-24
- **Autores:** Grupo do projeto

## Contexto

O ADR-025 passou a gerar o código por uma sequência de cada tipo (último do tipo + 5),
guardando cinco valores num arquivo. O grupo preferiu guardar um único valor, o último código
gerado, e chegar ao próximo código por uma conta direta, sem manter uma sequência por tipo.

## Decisão

> Vamos guardar só o último código gerado, de qualquer tipo, e calcular o próximo como o
> menor número depois dele cujo resto da divisão por 5 é o resto do tipo.

```
candidato = último + 1
distância = (resto do tipo − candidato) mod 5
próximo   = candidato + distância
```

- A distância é quantas casas faltam, a partir do candidato, até um número com o resto do
  tipo. O `Math.floorMod` garante que ela fica entre 0 e 4, mesmo quando a subtração dá
  negativo.
- O arquivo do caminho `Constantes.CODIGO_PATH` guarda só esse número (por exemplo, `17`).
  Sem o arquivo, o último é 0.
- Começando do 0, o primeiro código de computadores (resto 0) é 5, então o código 0000 nunca
  é gerado, sem precisar de um caso especial.
- O formato de 4 dígitos (`%06d`) continua.

Exemplo, começando sem arquivo:

| Cadastro | Resto | Último antes | Código gerado |
| --- | --- | --- | --- |
| Celular | 1 | 0 | 0001 |
| Computador | 0 | 1 | 0005 |
| Computador | 0 | 5 | 0010 |
| Bateria | 3 | 10 | 0013 |
| Outros | 4 | 13 | 0014 |
| Cabos | 2 | 14 | 0017 |

A conta foi conferida para todos os últimos códigos de 0 a 499 e os cinco tipos: o código
gerado sempre tem o resto do tipo, é maior que o anterior, fica no máximo 5 casas à frente e
nunca é 0.

## Alternativas consideradas

### Alternativa 1: Sequência por tipo, último do tipo + 5 (ADR-025)

- **Prós:** nenhum número desperdiçado.
- **Contras:** cinco valores guardados; o código não indica a ordem de cadastro.
- **Por que não foi escolhida:** o grupo preferiu um único valor e uma conta direta.

### Alternativa 2: Contador único avançando de um em um até achar o resto (ADR-004, ADR-013)

- **Prós:** fácil de entender.
- **Contras:** usa um laço; o contador `static` voltava a 1 a cada execução.
- **Por que não foi escolhida:** a conta chega ao mesmo número sem laço, e o valor fica salvo.

## Consequências

### Positivas

- Um único valor no arquivo, sem mapa por tipo.
- O próximo código sai de uma conta, sem laço.
- O código volta a indicar a ordem de cadastro.
- A conta é uma aplicação de aritmética modular: a distância até o próximo número da classe
  de congruência do tipo.

### Negativas

- Números ficam sem uso: entre dois cadastros, até 4 números podem ser pulados (no exemplo,
  2, 3, 4 e de 6 a 9).
- Com 4 dígitos, o limite de 9999 é compartilhado por todos os tipos.
- Continuam existindo duas fontes de verdade (o arquivo de código e o `residuos.json`); o
  laço do service que pede outro código se o gerado já existir continua como proteção.
- O último código é gravado antes de o resíduo ser salvo; se o cadastro falhar depois, aquele
  código fica perdido.
- O arquivo no formato do ADR-025 (um mapa por tipo) não é lido pela versão nova e precisa
  ser apagado.

### Neutras

- O gerador deixou de usar `EnumMap`, `TypeToken` e `GsonBuilder`.

## Riscos e pendências

- [ ] Apagar o arquivo de códigos no formato antigo antes de rodar a versão nova.
- [ ] Gravar o último código só depois de o resíduo ser salvo.

# ADR-024: Salvar os resíduos em arquivo JSON, com o Map em memória como fonte principal

- **Status:** Aceita
- **Data:** 2026-10-24
- **Autores:** Grupo do projeto

## Contexto

Até aqui, os resíduos ficavam só no `TreeMap` do repositório (ADR-011) e sumiam ao fechar o
programa. O grupo definiu que os dados serão salvos primeiro em arquivos JSON e, mais tarde,
num banco de dados. A camada de salvamento precisa poder ser trocada sem mexer no service.

## Decisão

> Vamos criar uma camada de persistência separada do repositório, que grava e lê a lista de
> resíduos num arquivo JSON formatado, usando a biblioteca Gson.

| Classe | Pacote | Papel |
| --- | --- | --- |
| `Persistencia<T>` | `Persistency` | Interface com `carregar()` e `salvar(List<T>)` |
| `PersistenciaArquivo<T>` | `backend_ecocode` | Implementação em JSON, genérica para qualquer tipo |
| `Constantes` | `Util` | Caminhos dos arquivos (`RESIDUOS_PATH`) |

- A persistência só lê a lista inteira e grava a lista inteira. Salvar, editar e excluir
  continuam sendo papel do repositório.
- O repositório cria a própria persistência num campo e carrega o arquivo **uma vez**, no
  construtor sem parâmetros, montando o `Map`.
- Depois disso, o `Map` é a fonte principal: `buscar` e `listar` leem só o `Map`; `salvar`,
  `editar` e `excluir` mudam o `Map` e chamam `gravar()`, que regrava o arquivo inteiro.
- `PersistenciaArquivo` recebe o caminho e a classe dos itens (`Residuo.class`), e monta o
  tipo "lista de T" com `TypeToken.getParameterized`, porque o Java não guarda o tipo do
  genérico em tempo de execução.
- O arquivo é gravado com pretty print e em UTF-8; a pasta é criada se não existir; se o
  arquivo não existir, `carregar()` devolve uma lista vazia; erros de leitura e escrita
  viram `UncheckedIOException` em vez de serem ignorados.

## Alternativas consideradas

### Alternativa 1: Um repositório completo para JSON, no lugar do repositório em memória

- **Prós:** uma classe a menos entre o service e o arquivo.
- **Contras:** salvar, editar e excluir seriam reescritos para JSON e de novo para o banco.
- **Por que não foi escolhida:** com a persistência separada, o repositório continua igual
  e só a forma de gravar muda.

### Alternativa 2: Persistência com salvar, editar e excluir por item

- **Prós:** parecida com o que um banco faz.
- **Contras:** repetiria a interface do repositório; num arquivo JSON, editar um item exige
  regravar o arquivo inteiro do mesmo jeito.
- **Por que não foi escolhida:** carregar tudo e salvar tudo é o que o arquivo permite.

### Alternativa 3: Ler o arquivo a cada consulta

- **Prós:** sempre reflete o arquivo, mesmo se for editado por fora.
- **Contras:** leitura de disco a cada busca. Uma primeira versão do código lia o arquivo no
  `listar()`, e o `gravar()` acabava regravando o conteúdo antigo, sem os dados novos.
- **Por que não foi escolhida:** o `Map` é a versão mais atual; o arquivo é só a cópia.

### Alternativa 4: Passar a persistência pelo construtor do repositório

- **Prós:** trocar JSON por banco exigiria mudar só quem monta as peças (o `Main`).
- **Contras:** exige mudar o construtor do repositório, o service, a tela e o `Main`.
- **Por que não foi escolhida:** o grupo preferiu não mudar como o repositório é criado.

## Consequências

### Positivas

- Os resíduos sobrevivem ao fechamento do programa.
- O JSON formatado pode ser aberto e conferido à mão.
- `PersistenciaArquivo<T>` serve também para os usuários, mudando só o caminho e a classe.

### Negativas

- O repositório fica preso ao JSON: para usar o banco, a linha que cria a persistência
  dentro dele precisa mudar.
- O arquivo inteiro é regravado a cada mudança.
- O Gson cria os objetos sem chamar o construtor, então as validações do `Residuo` não rodam
  na leitura; um JSON editado à mão com dados inválidos entra sem erro.
- Um JSON com erro de sintaxe lança `JsonSyntaxException` ao abrir o programa.
- O Gson não grava `LocalDate` sozinho nas versões recentes do Java; os usuários vão precisar
  de um adaptador para a data de nascimento.

### Neutras

- Primeira dependência do Gson no `pom.xml`.
- A ordem dos campos importa: a persistência é criada antes de o construtor carregar o `Map`.

## Riscos e pendências

- [ ] Os registros iniciais são cadastrados toda vez que o programa abre e agora se somam
  aos salvos; cadastrar só quando o repositório estiver vazio, ou removê-los.
- [ ] Tratar `JsonSyntaxException` e avisar que o arquivo está corrompido.
- [ ] Ao migrar para banco, avaliar o banco como repositório próprio, já que ele grava item
  a item.

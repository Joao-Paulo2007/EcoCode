# ADR-039: Colocar todo o código Java dentro do pacote raiz backend_ecocode

- **Status:** Aceita
- **Data:** 2026-10-27
- **Autores:** Grupo do projeto

## Contexto

Os pacotes ficavam soltos direto em `src/main/java`: `Domain`, `Service`, `Repository`,
`Tela`, `Util`, e assim por diante. Com o Spring Boot (ADR-038), isso vira um problema: o
`@SpringBootApplication` só procura componentes (`@Service`, `@Repository`,
`@RestController`) no pacote da classe de entrada e nos pacotes de dentro dele. Uma classe de
entrada sem pacote não é aceita pelo Spring.

O projeto também passou a ter duas partes, back-end (Java) e front-end (HTML, CSS e JS), e o
grupo quis que o nome deixasse claro qual é qual.

## Decisão

> Vamos mover todos os pacotes Java para dentro de um pacote raiz, `backend_ecocode`, com a
> `ServidorApplication` na raiz dele.

```text
src/main/java/backend_ecocode/
├── ServidorApplication.java      entrada do servidor (ADR-038)
├── Main.java                     entrada do terminal
├── Controller/                   TesteController
├── Tela/                         TelaCadastroResiduoTerminal
├── Service/                      GerenciarResiduosService, GerenciarUsuariosService
├── Repository/                   GerenciarResiduosRepository, GerenciarUsuariosRepository
├── Domain/                       Residuo, TipoResiduo, Usuario, CargoUsuario e as interfaces
├── Persistency/                  Persistencia e Files/PersistenciaArquivo
├── Exceptions/                   AcessoNegadoException
└── Util/                         cifras, Aritmetica, Configuracao, Constantes, validações
```

- Cada arquivo passou a declarar `package backend_ecocode.<Pacote>;`, e os `import` foram
  ajustados para `backend_ecocode.<Pacote>.<Classe>`.
- O front-end fica do lado, em `src/main/resources/frontend_ecocode` (ADR-041), com o mesmo
  padrão de nome.

## Alternativas consideradas

### Alternativa 1: Pacote no padrão de domínio invertido (`br.senai.ecocode`)

- **Prós:** é a convenção do Java e do próprio Spring Initializr.
- **Contras:** mais níveis de pasta; não deixa explícito que é a parte do back-end.
- **Por que não foi escolhida:** o grupo preferiu um nome que separa back e front. Pode ser
  trocado depois, se o professor pedir a convenção.

### Alternativa 2: Deixar os pacotes soltos e listar todos no `@SpringBootApplication`

- **Prós:** nenhum arquivo movido.
- **Contras:** cada pacote novo teria que ser lembrado na anotação; classe de entrada sem
  pacote continua não sendo aceita.
- **Por que não foi escolhida:** o pacote raiz resolve sem configuração.

## Consequências

### Positivas

- O Spring encontra sozinho todos os services, repositórios e controllers.
- Fica claro, pelo nome, o que é back-end e o que é front-end.

### Negativas

- Todos os arquivos Java mudaram de pasta e de `package`, o que gera um diff grande no Git e
  conflito com quem tinha alterações locais nos arquivos antigos.
- Os nomes de pacote continuam com inicial maiúscula (`Service`, `Domain`), o que foge da
  convenção do Java (tudo minúsculo). Não quebra nada, mas pode chamar atenção na correção.

### Neutras

- Os ADRs anteriores citam os pacotes sem o prefixo (`Util/CifraAfim`). Eles continuam
  valendo; o caminho completo hoje é `backend_ecocode/Util/CifraAfim`.

## Riscos e pendências

- [ ] Alguns ADRs antigos (ADR-014, ADR-024) e o README ficaram com textos como
  `backend_ecocode.Service/` depois de uma troca automática de nomes. Os ADRs aceitos não
  devem ser reescritos; o README já foi corrigido com a estrutura acima.

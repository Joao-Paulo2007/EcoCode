# ADR-009: Adicionar uma descrição opcional aos resíduos

- **Status:** Aceita
- **Data:** 2026-10-23
- **Autores:** Grupo do projeto

## Contexto

Os resíduos cadastrados não têm um campo para registrar informações extras quando isso
for necessário. Depois da refatoração, o tipo do resíduo passou a ser escolhido num menu
fechado (`TipoResiduo`), e o nome que o usuário digitava na versão 1.0 (ADR-006) deixou
de existir. Com isso, dois cadastros do mesmo tipo ficam indistinguíveis: um "Celular"
quebrado e um "Celular" com bateria estufada aparecem iguais na lista.

Por isso, foi proposta uma descrição de texto livre, não obrigatória.

## Decisão

> Vamos adicionar um campo de descrição opcional aos resíduos, para facilitar a
> identificação dos itens e permitir registrar informações importantes sobre cada um.

- A classe `Residuo` ganha o atributo `private String descricao`, recebido no construtor.
- Se a descrição vier nula, é guardada como texto vazio (`""`); se vier preenchida, os
  espaços das pontas são removidos com `trim()`.
- Na tela de cadastro, o usuário pode apertar Enter para pular a descrição, e ela só é
  exibida no resultado quando foi preenchida.

## Alternativas consideradas

### Alternativa 1: Manter sem descrição

- **Prós:** cadastro mais simples e rápido.
- **Contras:** não há como registrar notas ou informações relevantes sobre o resíduo.
- **Por que não foi escolhida:** a falta de descrição dificultaria adicionar informações
  no futuro e impediria diferenciar resíduos do mesmo tipo.

### Alternativa 2: Descrição obrigatória

- **Prós:** todo resíduo teria informações extras.
- **Contras:** obriga o usuário a escrever algo mesmo quando não há nada a acrescentar,
  o que tende a gerar textos sem valor ("nada", "-").
- **Por que não foi escolhida:** a maioria dos cadastros não precisa de detalhes; a
  descrição deve ajudar, não atrasar o cadastro.

### Alternativa 3: Campos específicos (marca, modelo, estado de conservação)

- **Prós:** dados estruturados, fáceis de filtrar.
- **Contras:** cada tipo de resíduo precisaria de campos diferentes, e o cadastro ficaria
  mais longo.
- **Por que não foi escolhida:** complexidade maior que a necessidade atual do projeto.

## Consequências

### Positivas

- Dá para diferenciar resíduos do mesmo tipo e registrar observações, como o estado do
  item ou cuidados no descarte.
- Recupera a informação específica que o texto livre da versão 1.0 permitia (ADR-006),
  sem perder a segurança do menu fechado de tipos.
- Como a descrição nunca fica nula, o restante do código pode usar `getDescricao()` sem
  verificar `null`.

### Negativas

- O construtor do `Residuo` e o `salvar` do service ganharam um parâmetro, e todos os
  pontos que os chamam precisaram ser atualizados.
- Por ser texto livre, a descrição não serve para filtrar ou classificar resíduos.
- Não há limite de tamanho; um texto muito longo pode bagunçar a listagem no terminal.

### Neutras

- Os registros iniciais de teste passam uma descrição padrão fixa.
- A tela de cadastro tem uma pergunta a mais, que pode ser pulada com Enter.

## Riscos e pendências

- [ ] Definir um tamanho máximo para a descrição, se a listagem ficar ilegível.
- [x] Incluir a descrição no `editar` (feito: Enter mantém a descrição atual).
- [ ] Se surgir a necessidade de filtrar por marca, modelo ou estado, revisar esta decisão
  em favor de campos específicos (Alternativa 3).

## Referências

- Classes `Residuo`, `GerenciarResiduosService` e `TelaCadastroResiduoTerminal`.

# ADR-022: Criar o módulo de usuários com CPF como chave e cadastro restrito a gerentes

- **Status:** Aceita
- **Data:** 2026-10-24
- **Autores:** Grupo do projeto

## Contexto

O sistema vai ter usuários com login. A regra definida pelo grupo é que ninguém se cadastra
sozinho: um gerente cria a conta e entrega os dados de acesso ao funcionário. O módulo foi
criado seguindo as mesmas camadas dos resíduos (ADR-010), mas **ainda não está ligado ao
menu**: nenhuma tela usa os usuários por enquanto.

## Decisão

> Vamos criar o módulo de usuários com as mesmas camadas dos resíduos, identificar cada
> usuário pelo CPF e permitir que só gerentes cadastrem e removam usuários.

| Classe | Pacote | Papel |
| --- | --- | --- |
| `Usuario` | `Domain` | Nome completo, CPF, e-mail, senha cifrada, cargo e data de nascimento |
| `CargoUsuario` | `Domain` | Enum com `GERENTE` e `FUNCIONARIO` |
| `GerenciarUsuariosService` | `Service` | Permissão por cargo, CPF repetido, busca com erro se não encontrar |
| `GerenciarUsuariosRepository` | `Repository` | `TreeMap` com o CPF como chave |
| `AcessoNegadoException` | `Exceptions` | Erro lançado quando o cargo não tem permissão |
| `ValidadorCpf` | `Util` | Validação do CPF |

- **Validações no `Usuario`:** cargo, nome e e-mail obrigatórios, CPF válido e data de
  nascimento no formato `dd/MM/yyyy`, convertida para `LocalDate`.
- **Regras no service:** só `GERENTE` cadastra e remove; não pode haver dois usuários com o
  mesmo CPF; `buscar` lança "Usuário não encontrado." em vez de devolver `null`.
- **Edição:** nome, e-mail e senha podem ser alterados; CPF, cargo e data de nascimento não.

## Alternativas consideradas

### Alternativa 1: E-mail como chave do repositório

- **Prós:** o login será por e-mail, então a busca do login iria direto na chave.
- **Contras:** o e-mail pode mudar, e o usuário pode editá-lo.
- **Por que não foi escolhida:** o CPF não muda e identifica a pessoa.

### Alternativa 2: Herança (`Gerente` e `Funcionario` como subclasses de `Usuario`)

- **Prós:** cada cargo poderia ter campos próprios.
- **Contras:** promover um funcionário exigiria trocar o objeto inteiro.
- **Por que não foi escolhida:** os cargos só diferem em permissão, e um enum resolve.

### Alternativa 3: Mais níveis de cargo (por exemplo, um administrador acima do gerente)

- **Prós:** separaria quem cadastra gerentes de quem cadastra funcionários.
- **Contras:** mais regras de permissão.
- **Por que não foi escolhida:** por enquanto, dois cargos atendem.

## Consequências

### Positivas

- Mesma organização dos resíduos, então o grupo já conhece o caminho tela, service e
  repository.
- Usuário com dados inválidos não chega a ser criado.
- A permissão fica no service, num lugar só.

### Negativas

- O login por e-mail vai precisar percorrer todos os usuários, já que a chave é o CPF.
- Como só gerentes cadastram, não existe forma de criar o primeiro gerente.
- O cargo de quem está cadastrando é passado como parâmetro; sem login, qualquer chamada
  pode se declarar `GERENTE`.

### Neutras

- O módulo existe no código, mas nenhuma tela o usa ainda.

## Riscos e pendências

- [ ] `listar()` do repositório devolve `List.of()`, sempre vazio; deve devolver
  `new ArrayList<>(usuarios.values())`.
- [ ] O CPF é validado duas vezes no construtor do `Usuario`; uma das checagens pode sair.
- [ ] Normalizar o CPF (só dígitos) antes de usar como chave, para que `123.456.789-09` e
  `12345678909` não virem dois usuários.
- [ ] Validar o formato do e-mail, impedir data de nascimento futura e exigir senha.
- [ ] Os setters de `editar` não validam; e-mail vazio passa na edição.
- [ ] Definir quem pode editar um usuário (hoje não há checagem de cargo no `editar`).
- [ ] Criar o primeiro gerente automaticamente quando não houver nenhum usuário.
- [ ] Corrigir a mensagem do `remover`, que diz "cadastro".
- [ ] Ligar o módulo ao menu, com login.

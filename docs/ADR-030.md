# ADR-030: Reunir as validações do resíduo na classe ValidacoesResiduos

- **Status:** Aceita
- **Data:** 2026-10-24
- **Autores:** Grupo do projeto

## Contexto

As validações do `Residuo` estavam escritas diretamente no construtor (ADR-014). As validações
do usuário passaram para uma classe própria, `ValidacoesUsuario` (ADR-028), e o grupo quis
manter o mesmo padrão nas duas entidades.

## Decisão

> Vamos reunir as validações do resíduo na classe `ValidacoesResiduos`, no pacote `Util`,
> seguindo o mesmo padrão da `ValidacoesUsuario`.

O método `validarResiduo(tipo, quantidade, codigo)` confere:

| Regra | Exceção |
| --- | --- |
| Tipo obrigatório | `IllegalArgumentException` |
| Quantidade maior que zero | `IllegalArgumentException` |
| Código só com dígitos, de 1 a 9 | `IllegalStateException` |

As regras são as mesmas do ADR-014; só mudou o lugar onde ficam. O código usa
`IllegalStateException` porque é gerado pelo sistema: se ele vier errado, é um bug do
gerador, não um erro de quem está cadastrando.

## Alternativas consideradas

### Alternativa 1: Manter as validações no construtor do `Residuo`

- **Prós:** nenhuma classe a mais.
- **Contras:** as duas entidades ficariam com padrões diferentes.
- **Por que não foi escolhida:** o grupo preferiu o mesmo padrão para resíduos e usuários.

### Alternativa 2: Uma classe única de validações para todas as entidades

- **Prós:** um arquivo só.
- **Contras:** a classe cresceria com regras que não têm relação entre si.
- **Por que não foi escolhida:** uma classe de validação por entidade é mais fácil de achar.

## Consequências

### Positivas

- Resíduos e usuários seguem o mesmo padrão de validação.
- As regras do resíduo ficam reunidas e fáceis de encontrar.

### Negativas

- O service ainda confere tipo e quantidade antes de gerar o código (ADR-014), então essas duas
  regras continuam escritas em dois lugares.
- Os resíduos lidos do arquivo não passam pelas validações, porque o Gson não chama o
  construtor (ADR-024).
- O `setQuantidade` usado no `editar` não passa pela validação.

### Neutras

- O parâmetro `tipo_residuo` usa underline, diferente do camelCase do restante do projeto.
- Os métodos poderiam ser `static`, já que a classe não guarda estado.

## Riscos e pendências

- [ ] Fazer o service usar a `ValidacoesResiduos` para tipo e quantidade, em vez de repetir as
  regras.
- [ ] Validar a quantidade também na edição.

## Referências

- Altera o ADR-014 no lugar onde as validações do resíduo ficam; as regras não mudam.
- ADR-028 (validações do usuário). `Util/ValidacoesResiduos`, `Residuo`.
